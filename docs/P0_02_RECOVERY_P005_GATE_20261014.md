## Real recovery incident: evidence and diagnosis limits

User reports: email received, initial redirect to localhost:5173 failed because Vite was down; after starting Vite, SET A NEW PASSWORD rendered. Submit displayed exactly: “Could not update your password. The link may have expired — request a new one.” No HTTP status/code collected. No recovery link, token or password was requested or recorded.

**Confirmed code defect:** `supabaseAuth.updateUserPassword` examined error_description/msg/error but omitted the standard GoTrue `message`. An HTTP 422 `{code:'same_password',message:'...'}` was reproduced against the actual extracted implementation: before fix 6/8 tests passed, two mirrored-copy regressions failed. Added `body?.message` to the error precedence in root and src App.jsx. After fix all eight passed. This restores diagnosis; it does not make invalid/expired tokens valid and does not establish the cause of the user's request.

Possible causes of that request, not proven:

1. Recovery access token expired while the local server was unavailable. Opening an already-consumed verification URL again can also report an invalid link. Need a fresh controlled attempt; do not reuse or share links.
2. Server-side rejection of reused/weak password or another auth policy, with the relevant `message` hidden by the confirmed bug.
3. Vite started with the wrong project's URL/key, or stale configuration. This machine's VITE URL was checked as exact TEST and key presence confirmed without exposing values; that does not prove the settings of the user's separate local machine. Restart Vite after configuration changes.
4. Server/rate-limit/authorization failure. HTTP status/code and sanitized message are needed to distinguish these; generic text alone cannot.

ERR_CONNECTION_REFUSED explains the initial unavailable frontend, not the subsequent API failure. Rendering the form only proves recovery hash parsing; it does not validate the JWT. There is no evidence to disable auth verification, relax password policies or change recovery credentials. The implementation still uses the official PUT /auth/v1/user with the recovery bearer only, does not refresh it automatically or persist it as a normal app session, and fails closed on the tested errors.
